# 财务垂直 RAG 调研：业界做法与我们的提升/补充清单

- 日期：2026-11-11
- 目的：在"只做年报/研报/招股书这类财务文档、往垂直深处做"的定位下，
  调研业界怎么做，对照我们四条纵深轴（口径引擎 / 表格解析 / 跨文档比较 /
  可核验），找出能提升、能补充的点。
- 方法：联网调研代表性方案 + **逐条对照本仓代码现状与留出集真实错题**，
  不空谈。所有"我们已有/缺口"均经代码或评测结果核实。

## 一句话结论

业界已经把"**语义元数据 RAG**"（给每段文本贴上"属于哪节/讲什么主题"的
标签再检索）做成财报问答标配，但普遍缺一层"**财务硬字段口径**"（这个数
到底是合并还是母公司、是归母还是扣非、单位是元还是百万）——而这层恰好
是我们实测里正在丢分的地方，也是我们能补、且能讲成差异化的地方。

## 一、别人怎么做的（4 个代表）

| 来源 | 核心做法 | 通俗解释 | 报告数字 |
|---|---|---|---|
| **FinSage**（财报专用 RAG，学术） | MinerU 解析 → **把表格改写成自然语言句子** → 四路检索（BM25+向量+元数据+HyDE）→ 交叉编码器重排 | 表格不再是一坨文本，而是"2024 年营业收入为 X 元"这样的句子，模型才读得懂 | FinanceBench 人工判 57% |
| **Metadata-Driven RAG**（arxiv 2510.24402） | 语境嵌入 + 两级语义元数据 + 检索前过滤 + 透明重排 | 每段前补一句"这段来自哪节、讲什么"再嵌入——**就是我们的 E5 语境增强** | F1 32.9→43.2；**反直觉：块扩展反而让幻觉 14.7%→22.2%** |
| **TextIn/xParse**（工业界） | 财务级结构化解析：跨页续接、层级还原、**字段绑页码+版面坐标** | 不只 OCR 认字，还要认出"这个数属于哪个表头" | 厂商自评，**无公开测试集** |
| **LedgerLens**（银行年报） | 多智能体"检索-分析-精炼"循环，角色拆分 | 一个 agent 抽数、一个核验、一个改写 | 自建 BAR-QA 上 94.1% F1 |

**两个关键 takeaway：**

1. Metadata 论文那个"**块扩展反而更差**"的发现，印证了我们 E8 的归因——
   更多上下文 ≠ 更好，我们没盲目堆 context 是对的。
2. 腾讯云《RAG 表格问答为什么总出错》点破一句要命的话：**"OCR 解决的是
   字符级，表格解析要解决的是字段级——这个数值属于哪个字段。"** 它举的
   审计案例：准确率从 92% 掉到 67%，系统返回的答案**看着对（有数字有
   引用），却绑错了字段**。这正是我们 id169/170 的病。
   （注意：此文是 xParse 厂商软文，星级自评、无公开方法，当 illustrative
   看，不当独立基准。）

## 二、对照四条纵深轴：已有什么 / 实测缺什么 / 能补什么

每条都对着代码现状与留出集真实错题核过。

### 轴 1 口径引擎 —— 推荐先做

- **业界**：TextIn 层级还原；金融数据集"六大质量维度"之首是口径统一性；
  CAS 30（财会〔2026〕11 号）/ IFRS 18 让口径**随年份变**。
- **我们已有**：`data/metrics.json` 21 指标 × 4 年，带别名/单位/值/页码，
  **已区分**营业总收入 vs 营业收入、净利润 vs 扣非净利润；`src/numeric.py`
  数字接地。
- **实测缺口**：**没有"合并 vs 母公司"这一维**。id169/170 模型取了母公司
  现金流量表/营收附注的数，和合并口径 gold 差一点；`src/ask.py` 提示里
  也没点明"默认合并"。
- **能补**：给 metrics.json 每个值加"合并/母公司"标签 + 提示默认合并 +
  口径随会计版本。**代价最小**（已有库加一维），直接修 2 道实测错题，
  且这正是 Metadata 论文自己点名缺的硬字段层。

### 轴 2 表格解析 —— 收益最大，建议第二步

- **业界**：FinSage 把表格改写成句子；xParse 输出带完整表头路径
  （`收入 > Q2: 1350 (单位:百万元)`）；MinerU 2.5 专门升级跨页/无边框表。
- **我们已有**：`data/extracted_tables_plus` 名字叫 tables，**其实是逐页
  纯文本**（page_001.txt），没有行列结构。
- **实测缺口**：相邻页 miss id150/151/210（分红跨 P33–34 只返回 P33）；
  **合计行假拒答** id175/191/219（单项答对、合计行却说未披露）。这就是
  腾讯云文说的"跨页表格断裂" + "字段级归属丢失"。
- **能补**：引入 MinerU 类结构化解析，把**表头路径 + 单位 + 跨页续接**绑进
  chunk。**代价中等**（换解析管线、重建索引），但修一批实测错题。核心
  认知：我们的数字接地目前是**字符级**，要升到**字段级**。

### 轴 3 跨文档比较 —— 建议靠后

- **我们已有**：`src/ask.py` `compare_years` 工具（同指标多年分别检索再
  合并），但只限茅台单公司。
- **实测**：跨年题修正口径 **15/15 全对**，单公司跨年已稳；跨公司/研报 vs
  年报还没建。
- **能补**：泛化成 `compare_documents`（多公司同指标），难点是**口径对齐**
  （不同公司"归母净利润"定义不同）。**代价大**（要多公司语料 + 口径映射），
  先放着。

### 轴 4 可核验 —— 护城河，不是短板

- **我们已有**：页级引用 + 数字接地 + **拒答 100%（3 倍样本复现）** +
  冻结留出集（sha256）+ CI 门禁 + 忠实度 LLM-judge 对抗校验。
- **实测缺口**：引用是**页级不是坐标级**；打分器口径偏差已修但只在离线
  重打里。
- **能补**：坐标级引用（字段绑版面位置），把"诚实评测"做成可对外展示的
  资产。**别人卷解析检索，我们卷可核验 + 诚实评测**——这恰是厂商自评
  做不到、Metadata 论文没做的。

## 三、差异化定位

FinSage / Metadata 论文强在**解析 + 检索 + 重排**，但元数据是**语义的**、
评测是**厂商自评或英文公开基准**。我们的护城河 =

1. **财务硬字段口径层**（指标 / 年份 / 合并 vs 母公司 / 单位）
2. **可核验**（拒答 / 页引用 / 数字接地）
3. **诚实评测**（冻结留出集双口径）

这三样正好是论文自己点名缺的。

## 四、推荐路线

1. **先做轴 1 的"合并 vs 母公司"维度**：改动最小、直接修 id169/170、
   能讲成"我们补了 SOTA 缺的硬字段层"的故事。
2. **轴 2 表格解析**第二步：收益更大但要重建索引。
3. 轴 3 跨文档、轴 4 坐标级引用靠后。
