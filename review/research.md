## A. 幻觉治理：从"给出处"到"可核验"

**A1｜ALCE：引用质量要单独评分** 【已验证】
来源：Gao 等，arXiv 2305.14627（2023-05-24）https://arxiv.org/abs/2305.14627
结论：第一个自动评估"带引用生成"的 benchmark，把答案正确性与引用质量拆开算——引的句子是否支持该论断。
对本项目：`src/evalcore.py` 只算 page_hit@k、MRR、page_prec@k（第 44-49 行），全是页级命中，没测"答案引的那条是否支撑该句"。建议加 citation precision，逐句判引用块是否支持这句话。

**A2｜Self-RAG：用反思标记决定要不要检索** 【已验证】
来源：Asai 等，arXiv 2310.11511（2023-10-17，ICLR 2024）https://arxiv.org/abs/2310.11511
结论：让模型生成反思标记，判断"是否需要检索、片段是否相关、生成是否被片段支持"，据此动态检索与引用。
对本项目：它需训练 critic，本项目不训练模型；同构轻量版可落地——在 `_agent_loop`（`src/ask.py:459`）加一次"证据够不够"的自评再决定是否续检，代价是多一次小调用。【判断】

**A3｜CRAG：先给检索打置信度再分档补救** 【已验证】
来源：Yan 等，arXiv 2401.15884（2024-01-29）https://arxiv.org/abs/2401.15884
结论：用轻量 retrieval evaluator 评估检索整体质量，分"正确/错误/模糊"三档，分别走知识精炼或外部搜索补救。
对本项目：`needs_agent`（`src/ask.py:427`）与拒答重试已是补救雏形，缺的是置信度判定。`RerankedRetriever`（`src/hybrid.py:139`）的分数可直接当 evaluator 阈值——这是把已写好的代码变成治理机制的最近路径。【判断】

**A4｜LongCite：句级引用才可核验** 【已验证】
来源：Zhang 等，arXiv 2409.02897（2024-09-04）https://arxiv.org/abs/2409.02897
结论：提出 LongBench-Cite 与句级引用方案，要求每句后标来源句子编号，而非段落末尾笼统给一个出处。
对本项目：现在答案模板要求在回答末尾标 `[来源: 2024年报 P8]`（`src/ask.py:30`），整段共用一处出处，跨页拼证据时无法核对哪句来自哪页。改成"每句末页级引用"后，A1 的校验才有落点。

**A5｜Anthropic Citations API：引用成了一等公民** 【已验证】
来源：Anthropic 平台文档 https://platform.claude.com/docs/en/build-with-claude/citations
结论：文档称 citations 返回"支持每个论断的确切段落"，以字符/页码位置的结构化字段返回，而非让模型自由生成引用串。
对本项目：说明结构化引用已是大模型 API 的产品方向；本项目自己拼引用串、用正则解析（`_CITE_RE`，`src/ask.py:164`），接云端时可直接吃结构化字段少一层脆弱逻辑。
备注：页面无日期，首发时间【未能核实】。

**A6｜AbstentionBench：拒答仍是未解问题** 【已验证】
来源：arXiv 2506.09038（2025-06-10）https://arxiv.org/abs/2506.09038
结论：20 个数据集（无答案、欠定义、假前提、时效过期等）×20 个前沿模型，拒答"未解决"，且单纯扩大规模收益有限。
对本项目：`RAG_REFUSAL_RETRY`（`src/ask.py:155-156`）方向对，但现在只识别拒答语义并重试一次，缺反向指标——"该拒答却硬答"的比例。

**A7｜VeriScore：拆到 claim 再核验** 【已验证】
来源：arXiv 2406.19276（2024-06-27），EMNLP 2024 Findings https://aclanthology.org/2024.findings-emnlp.552/
结论：先把长文拆成原子 claim，区分"可核验/不可核验"再逐条核验，比把每句都当事实更贴近真实生成。
对本项目：LLM-as-judge 容易把合理推断误判为幻觉。引入"不可核验"类别后判分口径更稳，也更便于解释。【判断】

## B. Agent 工具设计：工具少而准，评测要带成本

**B1｜ReAct：推理与行动交替仍是基本盘** 【已验证】
来源：Yao 等，arXiv 2210.03629（2022-10-06）https://arxiv.org/abs/2210.03629
结论：让模型交替生成推理轨迹与动作，把"想"和"调工具"织进同一个循环。
对本项目：`_agent_loop` 就是 ReAct 的工程版；建议加硬上限与早停，避免长尾成本。【判断】

**B2｜τ-bench：单次正确率会高估 agent** 【已验证】
来源：Yao 等，arXiv 2406.12045（2024-06-17）https://arxiv.org/abs/2406.12045
结论：提出 pass^k 度量多次试验一致性；实测前沿函数调用 agent（如 gpt-4o）成功率不足 50%，零售场景 pass^8 不足 25%。
对本项目：agent 路径只测单次答对，compare_years 这类多步链路的稳定性没被度量。建议挑 10 道 agent 题跑 3 次，报"至少 2 次对"的比例。

**B3｜BFCL V4：工具评测连成本与延迟一起报** 【已验证】
来源：伯克利 Gorilla 团队，榜单页 Last Updated 2026-04-12，论文 ICML 2025 https://gorilla.cs.berkeley.edu/leaderboard.html
结论：V4 从"函数调用准确率"扩到整体 agentic 评测，并同时给出整轮评测的 cost（美元估算）与 latency（秒）。
对本项目：坐实"工具能力必须和成本/延迟一起评"。本地 Qwen3-4B 工具调用弱正是 `needs_agent` 零成本路由的理由，但路由是手写正则（`src/ask.py:414-439`），加工具时易漏。

**B4｜Agentic RAG 综述：工具集是并列能力** 【已验证】
来源：arXiv 2501.09136（2025-01-15）https://arxiv.org/abs/2501.09136
结论：把 agentic RAG 归为反思、规划、工具使用等范式；工具维度上检索/读取/计算/对比是并列能力，不是检索的附属。
对本项目：三个工具里没有 calculator，也没有表格结构化取数。年报大量"同比增减""占比"需要算术，现在只靠提示词要求"计算得出要注明"（`src/ask.py:320`），属约束而非机制。

**B5｜Building effective agents：先简单后自主** 【已验证】
来源：Anthropic 工程博客（2024-12-19）https://www.anthropic.com/engineering/building-effective-agents
结论：成功案例多用简单可组合模式而非重框架，明确区分 workflow 与 agent；附录专讲"像给新同事写文档一样写工具描述"。
对本项目：与 `needs_agent` 的"能直通就不 agent"同向。可改的是工具描述——现在只写用途，没写"何时不要用"，模型易对单年事实题滥用 compare_years。

**B6｜Contextual Retrieval：一半收益在 rerank** 【已验证】
来源：Anthropic（2024-09-19）https://www.anthropic.com/news/contextual-retrieval
结论：语境嵌入 + 语境 BM25 把检索失败率降低 49%，再接 rerank 降到 67%；配合 prompt caching，语境化一次性成本约 $1.02/百万文档 token。
对本项目：E5 只做前半段，rerank 停在实验等于放弃另一半收益。按 1761 块约 0.18M token 估算，重跑成本约 $0.2 量级（复算，属【判断】）。

## C. 财报问答：难度不在检索，在数值与证据链

**C1｜FinQA：数值题要有标准算式** 【已验证】
来源：Chen 等，arXiv 2109.00122（2021-09-01）https://arxiv.org/abs/2109.00122
结论：面向财报的数值推理数据集，答案附带可执行运算程序（program）作金标。
对本项目：50 题若只存最终数字，就分不开"算错"与"检索错"。给算术题补一行算式金标，评测即可分开归因。

**C2｜TAT-QA：表格与文本一起评** 【已验证】
来源：Zhu 等，arXiv 2105.07624（2021-05-17）https://arxiv.org/abs/2105.07624
结论：表格 + 文本混合问答，答案分抽取式、算术式、计数式三类。
对本项目：这三类可直接拿来自检覆盖度；E7 系列做了表格处理，但金标集里表格题占比与三分类覆盖需显式统计。【判断】

**C3｜DocFinQA：全文档问答是真的难** 【已验证】
来源：arXiv 2401.06915（2024-01-12）https://arxiv.org/abs/2401.06915
结论：把 FinQA 扩到全文档，上下文从不足 700 词扩到 123k 词；检索式管线与长上下文模型都仍吃力，文档越长越差。
对本项目：556 页、1761 块正落在它指出的困难区。这是"不能把整本年报塞进上下文"的一手证据，检索层仍是主战场。

**C4｜FinanceBench：简单题也会大面积失败** 【已验证】
来源：Islam 等，arXiv 2311.11944（2023-11-20）https://arxiv.org/abs/2311.11944
结论：10,231 道公开公司财报题；150 例人工复核中，GPT-4-Turbo 配检索有 81% 答错或拒答；更长上下文能提升，但企业场景延迟不可接受。
对本项目：给"简单题也难"和"长上下文能提分但不是生产方案"提供论据。README 不宜暗示 62% 页码命中已接近行业水平。

**C5｜FinBen：财务能力不止问答** 【已验证】
来源：arXiv 2402.12659（2024-02-20）https://arxiv.org/abs/2402.12659
结论：36 个数据集、24 项任务，含 RAG 与 agent 评测；LLM 强于信息抽取与文本分析，弱于复杂推理与预测。
对本项目：若要讲完整能力，挑 2–3 个子任务对齐即可，不必自证全面。【判断】

**C6｜CFBenchmark：中文口径参照** 【已验证】
来源：arXiv 2311.05812（2023-11-10）https://arxiv.org/abs/2311.05812
结论：中文金融助手 benchmark，按金融文本理解、生成等基础能力分项评测。
对本项目："中文年报 + 页码级引用"这一形态我没找到公开 benchmark（【未能核实】），所以自建 50 题必要，但判分脚本与出题口径应公开。

**C7｜AlphaSense：结构化数据 + 原文一起接地** 【已验证】
来源：AlphaSense 帮助中心，页面更新 2026-03-24 https://help.alpha-sense.com/hc/en-us/articles/48564174120595-Financial-Data-Integration-into-Generative-Search
结论：把结构化财务数据（含 Canalyst 口径）、公司 KPI 与年报/纪要合并，答案同时接地于财务数据与原始文档；同站另有"Deep Research"自主多步研究。
对本项目：产品形态已从"检索+引用"走到"结构化指标层+原文+多步研究"。本项目缺的正是中间这层指标表——有了它，换算与同比可查表而非靠模型。

**C8｜Hebbia：引用即产品** 【已验证】
来源：Hebbia 博客（2025-07-10）https://www.hebbia.com/blog/5-ways-equity-research-teams-use-hebbia-to-drive-speed-and-insight
结论：主打上传上千份文档后输出"带引用链接的结构化结果"，可直接进模型与底稿，卖点是能扛内部与客户质询。
对本项目：可追溯本身是交付物。把 `[来源: 2024年报 P123]` 做成可点击跳转、可复制成证据清单，是很便宜的产品化动作。

## D. 工程化：合规边界、可观测性与 CI 的真实门槛

**D1｜生成式 AI 暂行办法：只管"向公众提供"** 【已验证】
来源：网信办等七部门第 15 号令，2023-07-10 公布、2023-08-15 施行 https://www.gov.cn/gongbao/2023/issue_10666/202308/content_6900864.html
结论：第二条只适用"向境内公众提供"的服务，企业内部研发应用不适用；第十七条只有具舆论属性或社会动员能力的服务才需安全评估与算法备案；第十二条要求按深度合成规定标识生成内容。
对本项目：本地/自用不在规制内，可写进 README；对外提供服务才触发备案与标识义务。【判断】

**D2｜生成合成内容标识办法：文本也要标** 【已验证】
来源：国信办通字〔2025〕2 号，2025-03-07 成文，第十四条自 2025-09-01 施行 https://www.gov.cn/zhengce/zhengceku/202503/content_7014286.htm
结论：显式标识（文本首尾或界面显著提示）+ 隐式标识（元数据写入属性、服务方编码、内容编号）双轨，导出复制也要带标识。
对本项目：做成对外产品时答案文本需显式标识位；本地自用不触发。接口层加一个字段即可，成本极低。

**D3｜银行保险数据安全办法：卖给机构才是门槛** 【已验证】
来源：金融监管总局 金规〔2024〕24 号，2024-12-27 印发 https://www.gov.cn/gongbao/2025/issue_11906/202503/content_7011160.html
结论：适用对象是银行保险机构，要求建数据安全治理体系、分类分级与全生命周期管控。
对本项目：只用公开年报不受它约束；若客户是金融机构，分类分级、日志留存、审计留痕会变硬需求——这也是"可追溯引用"商业价值的来源。【判断】

**D4｜OWASP LLM Top 10 2026：四条直接命中** 【已验证】
来源：OWASP GenAI Security Project，2026 版 2026-08-04 发布 https://github.com/GenAI-Security-Project/GenAI-LLM-Top10
结论：2026 排序为 LLM01 提示注入、02 敏感信息泄露、03 过度自主、04 供应链、05 数据与模型投毒、06 无界消耗、07 错误信息、08 隐藏上下文泄露、09 向量与嵌入弱点、10 输出处理不当。
对本项目：07（数字幻觉）、09（向量库）、10（答案直接渲染）、03（工具越权）四条直接对应现有代码。工具参数有年份白名单校验（`src/ask.py:362`），但输出侧在 `src/api.py` 里 grep 不到转义或长度处理。

**D5｜OpenTelemetry GenAI 语义约定：trace 有标准字段** 【已验证】
来源：OTel 文档已迁移至新仓库 https://github.com/open-telemetry/semantic-conventions-genai
结论：GenAI 约定独立成库，覆盖 span/metric/event，并含 MCP 与各 provider（含 OpenAI）约定。
对本项目：现在只有 `.log` 与 `results/*.json`，没有"一次问答 = 一条 trace"。按这套字段记检索耗时、工具次数、token，才能回答"多花 0.3 秒换 5 个点命中值不值"。【判断】

**D6｜promptfoo GitHub Action：断言进 CI** 【已验证】
来源：promptfoo 文档 https://www.promptfoo.dev/docs/integrations/github-action/
结论：官方 Action 把评测用例与阈值断言跑进 CI，不达标即失败。
对本项目：`eval-gate.yml` 已把检索层做成免费 gate（64%），答案层因成本只在手动时跑（同文件 51–53 行）。下一步可做夜间采样 10 题的低成本答案层 gate。【判断】

## 如果只做 5 件事，按投入产出排序

1. **reranker 上生产，用其分数做检索置信度分档**（A3）：代码已在 `src/hybrid.py:139`，只差接线与阈值；"模糊"档接上现有扩检重试，等于最小改动拿到 CRAG 一半。
2. **句级引用 + 引用支持性校验**（A1/A4）：把"整段一个出处"改成"每句一个出处"并加 citation precision，是把"页码命中"升级为"内容真被支撑"，也是对外最能讲的差异点。
3. **加 calculator 与表格取数工具**（B4/C7）：把换算与同比从提示词约束变成工具约束，直接消掉 `_grounding_fix` 最常修的那类错误（`src/ask.py:174-176` 的注释正是"抄错一万倍"）。
4. **补两个评测维度：pass^k 与过度回答率**（A6/B2）：10 道 agent 题跑 3 次看"至少 2 次对"；再造 10 道无答案题测"该拒答却硬答"。两项都不必上云端。
5. **按 GenAI 语义约定记 trace**（D5）：一次问答记检索耗时、工具链、token 与成本，让"要不要上 rerank""要不要多一轮检索"变成可算的账。

前三件都落在已有代码上、不引入新服务；第 4 件补测量；第 5 件让前四件以后可被持续证明。相反，"长上下文替代检索""换更大嵌入模型"这类动作，按 C3/C4 的证据在当前规模上回报最低。
